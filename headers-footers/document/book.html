Names and URLs

Use plural nouns for collections, for example /orders and /customers. Use the ID of an item after the collection: /orders/ord_81f2.

Use lowercase letters and hyphens in URLs. Use camelCase for JSON fields. Do not put verbs in a URL. The HTTP method is the verb.

  • GET /orders lists orders.
  • POST /orders creates an order.
  • GET /orders/{id} gets one order.
  • PATCH /orders/{id} changes some fields of one order.
  • DELETE /orders/{id} deletes one order.

An action that is not create, read, update or delete gets its own sub-resource, for example POST /orders/{id}/cancellation.

Errors

Every error response has a JSON body with a code and a message. The code is stable, and clients can use it in their logic. The message is for people and can change.

The table lists the status codes that the APIs use, with one example code for each.

StatusExample codeWhen
400invalid_fieldA field has the wrong type or format.
400missing_fieldA required field is missing.
401invalid_keyThe API key is missing or wrong.
403not_allowedThe key cannot do this action.
404not_foundThe item does not exist, or the key cannot see it.
409conflictThe item changed after the client read it.
413body_too_largeThe request body is over the limit.
415wrong_content_typeThe body is not JSON.
422invalid_stateThe item is in a state that does not allow the action.
429rate_limitedToo many requests. Read the Retry-After header.
500internal_errorAn error on the server. Retry later.
503unavailableThe service is down for a short time. Retry later.

Return all field errors in one response, not only the first one. Each field error has the name of the field, so a form can show the error next to the right input.

Do not put stack traces, SQL or internal host names in an error message. Write the details to the server log, with a request ID. Return the same request ID in the Request-Id header, so support can find the log entry.

Use status 404 when a key asks for an item that belongs to another account. Status 403 tells the caller that the item exists.

Retry rules for clients:

  • Retry 429, 500 and 503 responses, with a wait time that doubles after each attempt.
  • Do not retry 400, 401, 403, 404, 409, 413, 415 or 422 responses without a change.
  • Send an Idempotency-Key header with each POST, so a retry does not create a second item.

Log each error response with its status, code, request ID and the time the request took. A rise in one code is often the first sign of a problem in a client or in a new release.

Document every error code in the API reference, with an example body and the action that fixes it. A client developer reads this page when a request fails, not before.

Keep the old codes when you add new ones. A client can have logic for each code, so a renamed code is a breaking change.

Test the error responses as you test the success responses. Each endpoint needs at least one test for a missing field, one for a wrong type and one for a key without access.

Pagination

List endpoints return at most 100 items. The client asks for the next page with the cursor value from the last response. A cursor stays valid for 24 hours.

Do not use page numbers for large lists. When items are added during the reads, page numbers skip or repeat items. A cursor does not.

  • limit: the number of items, from 1 to 100. The default is 20.
  • cursor: the value of nextCursor from the last page.
  • nextCursor: null on the last page.

Versions

The URL has the major version: /v2/orders. A new field in a response is not a breaking change. A removed field, a renamed field or a new required field is.

Announce a breaking change six months before the old version stops. Send the Sunset header with the stop date on each response of the old version.
